# 系统定性评估报告

## 评估概要

- **评估时间**：2026-08-15
- **分析来源**：docs/deconstruct/*（设计解构）、docs/review/code-review-20260815-001-rust.md（代码审查）、docs/dup/dup-2026-08-15-001.md（重复度）、docs/detect/detect-20260815-001.md（问题侦测）
- **系统名称**：Bamboo Pipe Engine (BPE)

## 维度评分（1-5分）

### 1. 设计维度：3分

**倾向**：面向机器（性能优先，无 GUI/CLI，纯 API 接口）
**关键特征**：

- API 面（def_incoming/def_mapper/new_data）简洁，纯机器接口，无人工交互层
- 性能设计（环形缓冲 + JIT + 零分配回调）完全为吞吐而生
- 错误处理走日志 + Option，无面向人的友好提示
- 但内部状态以全局裸指针 + Box::leak 组织，封装与安全性让位于性能

### 2. 开发维度：2分

**模式**：混合（模块边界清晰，但扩展机制断裂）
**关键特征**：

- 模块划分（SQL/JIT/exec/mapper/aggregate）本身清晰
- 但扩展点失效：多 mapper 不生效、多聚合不可绑定、动态定义泄漏 JIT 引擎
- 跨语言靠 JNI/PyO3 各写一份镜像代码，无代码生成
- 测试以"复制模板改 SQL"方式扩展，不可持续

### 3. 运维维度：1分

**自动化程度**：全人工
**关键特征**：

- 无 CI/CD 配置、无监控指标、无健康检查
- 无持久化、无状态导出/恢复
- 无部署产物管理（wheel 手动安装）
- 日志为唯一可观测手段

### 4. 非功能属性

**健壮性**：差。外部输入（非法 SQL 列名、超长数据、除零）可 panic→abort 终止宿主 JVM/Python 进程；窗口回绕后处理能力坍缩；聚合结果错误。
**可维护性**：中。注释详尽、风格统一、模块职责清晰，但全局状态散落 10+ 处 static mut、测试无断言、脚手架 31.8% 重复。
**性能**：设计优、实现次。未回绕时热路径达标（JIT 过滤 ~ns 级、Rust 回调零分配）；回绕后坍缩为 1 条/次，聚合 O(n²)，长期运行性能不可信。

## 领域识别

### 系统类型

**识别结果**：基础设施类（流式数据处理引擎 / CEP 中间件），面向 Java/Python/Rust 开发者嵌入使用
**核心价值**：以 SQL 定义规则、以 JIT 获得纳秒级过滤延迟的嵌入式单表流处理引擎

### 领域匹配度

**匹配程度**：部分匹配
**合理性分析**：

- 匹配：面向机器的 API 设计、性能优先的架构取向、多语言绑定策略，均符合嵌入式引擎定位
- 不匹配：**基础设施级系统要求"高可用、强一致、可扩展"**，而 BPE 单线程、无持久化、正确性缺陷（回绕/聚合/多规则）未达基础设施门槛
- 风险分析：作为引擎被嵌入宿主应用（尤其 JVM），其 abort 行为与错误结果会直接污染宿主，风险被放大

## 尖锐总结（约460字）

**一句话定性**：BPE 是一台"性能思路正确、正确性未完工"的单表流过滤原型机——用 LLVM JIT 和环形缓冲证明了速度，却用全局裸指针和未初始化的聚合证明了它还没准备好被嵌入任何生产系统。

**设计倾向批判**：它以极端方式践行"面向机器"——static mut 全局状态、Box::leak 永生对象、get_mut 别名 UB、外部输入 unwrap 后 release abort。这些选择换来的是热路径零分配，代价是 Rust 的安全承诺全部悬空。当一次非法 SQL 能杀死宿主 JVM 时，"性能优先"已从工程取舍滑向事故源头。

**开发模式评价**：模块划分可圈可点，但扩展机制是断裂的——多 mapper 只有第一个生效、多聚合只有第一个可绑定、动态定义逐次泄漏 LLVM 引擎，这些不是编码失误，是身份体系与生命周期设计的整体缺失。测试 31.8% 重复且零断言，等于给这套断裂架构盖了"全绿"的假章。

**运维现状警示**：全人工、零监控、零恢复能力。引擎没有持久化，重启即失忆；stop() 是空壳，资源永不释放；唯一可观测手段是日志。作为基础设施，这是不可接受的。

**非功能短板**：健壮性最致命——回绕坍缩（实测 2048 条后只处理 1 条）、聚合二次增长、OOB panic 三点叠加，长期运行的正确性与可用性均无保证。

**领域匹配判断**：设计取向（面向机器、性能优先）与嵌入式引擎定位匹配，但"强一致、高可用、可扩展"的基础设施底线远未达到，属部分匹配。

**最大风险**：不是性能，而是"演示场景全绿、生产场景塌方"的假安全感——现有测试体系无法暴露任何正确性缺陷。

**关键改造建议**：如果只能改一处，先把聚合与窗口语义修正并补上断言测试（refactor Phase 1），让引擎在真实数据量下"算得对"，再谈速度。
