## 维度评分（对比 08-15）

### 设计：3 → 4
面向机器的定位贯彻到底；本次补上"回调与热路径解耦"这块架构拼图（无界 egress、async-only Java API、watchdog 旁路计时——卡死线程自身无法超时这一约束被正确处理）。仍扣分：static mut 全局态与 Box::leak 永生对象未变，Rust 安全承诺仍部分悬空。

### 开发：2 → 3
扩展点断裂已修复（多 mapper/多聚合成型，标量函数 reg! 宏注册 15+）；跨语言仍为手写镜像（bpe4j/bpe4py 各一份），无代码生成。测试从"零断言冒烟"提升为 56 Rust 断言测试 + 7 Java 验收（含异步正确性 845 条全量核对、watchdog 告警载荷合法性）。

### 运维：1 → 2
watchdog 三策略（Drain/Failover/AlertOnly）是引擎内建的自愈能力，alert listener 可桥接外部监控——这是从"全人工"到"半自动故障处置"的实质一步。但 CI/CD、持久化、状态恢复仍然为零，重启即失忆未变。

### 非功能属性

- **健壮性**：回调死锁从"冻结引擎线程"变为"watchdog 检测 + 策略自愈 + 无界不丢"。除零/非法 SQL panic 路径未复测，维持"中下"判断。
- **性能**：0.31µs/op、2.3M rec/s、Esper 1.8-4.5× 均为**同步回调时代**数字；异步化后热路径新增 channel send + 每事件 Box 分配（payload 拷贝本来就有，增量主要是分配+send ~50-100ns 量级），**全路径数字需重测后方可对外引用**。这是当前价值评估中最大的未知数。
- **可维护性**：中。egress 单文件 480 行承载队列+watchdog+三策略+测试，职责已偏重。

## 领域匹配度

**识别**：嵌入式风控/告警预过滤内核（特化单表规则引擎），非通用 CEP 平台。
**匹配**：**基本匹配**（从"部分匹配"上调）。理由：该场景的核心要求是"高频进、异步出、回调不拖垮引擎、故障可自愈、数据不丢"——本次编码后五项全部成立。基础设施级"高可用/强一致/可扩展"要求不适用于嵌入内核定位，属合理让渡。

## 尖锐总结（约 420 字）

**一句话定性**：BPE 已从"性能思路正确、正确性未完工的原型机"毕业为"可被嵌入试点的风控预过滤内核"——速度证明过了，正确性修完了，回调通道这次也通了，但它仍然是一台没有持久化、没有发版纪律、性能数字过期的单核机器。

**价值增量**：本次 egress 三件套（无界不丢、watchdog 三策略、Java async-only）补的不是功能，是**生产可用性的下限**——回调死锁从致命伤降级为可观测、可自愈的运行时事件。这是"演示"与"试点"之间的分界线。

**价值边界**：它的真实价值在"公司内风控/告警链路的前置过滤层"这一特化生态位，配合既有 CEP（BPE→Esper 级联）而非替代。作为开源项目，赛道被 Esper/Flink 压制，README 的边界声明已经承认这一点。

**最大风险**：一是异步化后的性能数字未重测，旧 benchmark 不可再引；二是运维短板（零持久化、零 CI）没有随功能补齐；三是 0.3.0-dev 至今未发版，无版本纪律的引擎不配被生产依赖。

**改造优先级**：重测异步路径性能（半天）→ 0.3.0 发版 + CHANGELOG（一天）→ 真实负载试点（一周），三者完成后"实际价值"才能从代码资产兑现为工程资产。
